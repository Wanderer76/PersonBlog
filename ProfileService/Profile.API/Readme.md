# План разработки страницы профиля

## Цель и согласованные решения

Реализовать страницу по согласованному макету `index.html` в корне репозитория. Отделить личный профиль от управления блогом и подготовить подключение друзей и сообщений через фичефлаги бэкенда.

- `/profile` показывает человека: аватар, имя, логин, интересы и дату регистрации.
- В блоке «Обо мне» остаются только «Интересы» и «На сайте с». Город, личный сайт и описание под именем не добавлять.
- Аватары пользователей и блога круглые, без белого кольца. Логотип — текст PlayView в существующем стиле приложения, без дополнительного значка.
- Нажатие на аватар в хэдере открывает меню профиля и управления блогом.
- При регистрации у пользователя нет блога. Вместо демонстрационной карточки показывается предложение создать блог.
- Друзья и сообщения появятся позже. Их элементы интерфейса зависят от вычисленных на сервере флагов.
- Новый контроллер аккаунта не создавать. Контекст возвращает существующий `ProfileController` в Gateway.
- Контекст предусматривает разрешения на публикацию видео и текстов. Система модераторских ограничений — последующий этап.

Данные и числа из макета являются демонстрационными и не переносятся в приложение как значения по умолчанию.

## 1. Ответственность компонентов

Этот план хранится в `ProfileService/Profile.API`, но реализация затрагивает ProfileService, Gateway, BlogService и frontend.

| Компонент | Ответственность |
| --- | --- |
| ProfileService | Хранение и редактирование данных человека |
| Существующий ProfileController в Gateway | HTTP-контракт профиля и нового контекста |
| Сервис сборки контекста в Gateway | Получение состояния блога, вычисленных флагов и разрешений |
| BlogService | Данные блога и обязательные проверки действий с публикациями |
| Frontend | Отображение данных, навигации и доступных действий |

Не помещать всю сборку контекста в контроллер. Не добавлять BlogService знания о друзьях и сообщениях. Не обращаться из Gateway напрямую к базам микросервисов.

## 2. Контракты API

### Данные человека

Сохранить существующий `GET /api/Profile/my` в Gateway и расширить возвращаемую модель необходимыми данными:

- имя;
- URL аватара;
- логин для строки `@admin`, если он доступен из авторитетного источника аккаунтов;
- интересы;
- дата регистрации.

В `ProfileModel` добавлены `CreatedAt` и `Interests`. На текущем этапе `Interests` — пустой список строк. Хранение, миграцию и редактирование интересов отложить; в интерфейсе показывать «Не указаны». Не подставлять вымышленные интересы пользователю.

До реализации определить источник логина и даты регистрации. У `AppProfile` есть унаследованный `CreatedAt`, но профиль создаётся через событие: это время может отличаться от регистрации аккаунта. Использовать достоверную дату регистрации; при необходимости передавать её в событии регистрации и сохранять в профиле. Для существующих пользователей определить перенос данных без выдуманных дат. Не использовать дату создания блога.

Если поле не заполнено, показывать корректное пустое состояние. Отсутствующий логин не заменять именем пользователя или фиктивным `@admin`.

### Контекст профиля

Добавить в существующий `Gateway.API.Controllers.ProfileController`:

```http
GET /api/Profile/context
```

Пример ответа для пользователя с блогом:

```json
{
  "blog": {
    "hasBlog": true,
    "id": "8246300e-394c-4455-a751-8849c05e2b16"
  },
  "features": {
    "friendsEnabled": false,
    "messagesEnabled": false
  },
  "permissions": {
    "publishVideo": {
      "isAllowed": true
    },
    "publishText": {
      "isAllowed": true
    }
  }
}
```

Для пользователя без блога:

```json
{
  "blog": {
    "hasBlog": false,
    "id": null
  },
  "features": {
    "friendsEnabled": false,
    "messagesEnabled": false
  },
  "permissions": {
    "publishVideo": {
      "isAllowed": false
    },
    "publishText": {
      "isAllowed": false
    }
  }
}
```

Правила контракта:

- `hasBlog` и `id` согласованы и получены из одного актуального результата: отсутствие блога означает `false` и `null`.
- Не трактовать таймаут или ошибку BlogService как отсутствие блога. При невозможности собрать достоверный контекст возвращать явную ошибку; frontend предлагает повторить запрос.
- `features` содержит только разрешённые к раскрытию, вычисленные для текущего пользователя значения. Списки участников эксперимента и внутренние правила не передаются клиенту.
- На текущем этапе оба разрешения в `permissions` равны `blog.hasBlog`. Это предварительная доступность действий в интерфейсе, а не полноценная политика ограничений.
- Использовать имя `isAllowed`. Поле `reasonCode` пока не добавлять.
- Ответ персональный. Не кэшировать его совместно для разных пользователей; в первой версии не использовать публичный HTTP-кэш.
- Старый `/api/Blog/hasUserBlog` сохранить до перевода потребителей. Удалять только после проверки отсутствия обращений.

## 3. Фичефлаги

Фичефлаг управляет включением функции продукта. Наличие блога является состоянием данных, а запрет публикации конкретному пользователю — разрешением. Не смешивать эти понятия.

Сейчас оба флага захардкожены в `false`; для текущего этапа это согласованное решение. Следующим этапом подключить `Microsoft.FeatureManagement` и конфигурацию приложения. Подключение Azure и отдельная админка управления флагами не требуются.

| Внутренний флаг | Поле контекста | Начальное значение |
| --- | --- | --- |
| Friends | friendsEnabled | false |
| Messages | messagesEnabled | false |

- Вычислять флаги на бэкенде через выделенный сервис.
- Первоначально менять значения через конфигурацию с перезапуском сервиса. Обновление без перезапуска не является требованием первого этапа.
- Отсутствующий флаг считается выключенным. Ошибку сборки контекста не маскировать фиктивным успешным ответом.
- В качестве последующего эксперимента добавить включение только для выбранных пользователей. Идентичность получать через `ICurrentUserService`.
- Не помещать флаги в JWT: они должны обновляться без перевыпуска токена.
- Не включать в рабочем окружении флаг функции, экран и API которой ещё не реализованы.

Документация: [Microsoft Feature Management](https://learn.microsoft.com/en-us/azure/azure-app-configuration/feature-management-dotnet-reference).

## 4. Разрешения на публикации

Предусмотреть независимые действия `publishVideo` и `publishText`. В первой версии Gateway присваивает обоим `isAllowed = hasBlog`, поскольку в BlogService пока нет механизма вычисления разрешений. Новую систему ограничений для запуска страницы не создавать. Существующие серверные проверки операций сохраняются.

Расширение для будущих ограничений:

| Ограничение | publishVideo | publishText |
| --- | --- | --- |
| Нет ограничений и выполнены условия публикации | Разрешено | Разрешено |
| Запрещены видео | Запрещено | Определяется остальными правилами |
| Запрещены тексты | Определяется остальными правилами | Запрещено |
| Запрещены все публикации | Запрещено | Запрещено |
| Нет блога | Запрещено | Запрещено |

Следующие требования относятся к будущей системе ограничений. Общий запрет имеет приоритет над разрешениями отдельных типов. Формат причин отказа определить при реализации этой системы; сейчас `reasonCode` не нужен.

- Контекст и API публикаций должны использовать один источник правил и ограничений, без двух независимо реализованных политик в Gateway и BlogService.
- Разместить вычисление бизнес-разрешений на стороне владельца операций публикации; Gateway получает готовый результат через контракт сервиса.
- Проверять разрешения на сервере при выполнении операции, даже если frontend ранее получил `isAllowed: true`.
- Сохранить проверки авторизации, владения блогом и пользовательского контекста. Флаги и разрешения не заменяют эти проверки.
- Различать создание черновика, загрузку файла и публикацию. Запрет публикации не должен неявно запрещать остальные действия. При реализации сопоставить правила с фактическими endpoint'ами проекта.
- Если публикация отложенная или асинхронная, повторно проверять действующие ограничения в момент публикации.
- Будущая система ограничений может хранить тип запрета, причину, срок действия и аудит. Её хранилище, модераторский UI и выдача запретов не входят в первый этап страницы.

## 5. Страница профиля и навигация

### Профиль

- `/profile`: карточка человека, блок «Обо мне», компактная карточка блога либо предложение создать его.
- `/profile/edit`: редактирование имени и аватара; редактирование интересов отложено, дата регистрации не редактируется пользователем.
- Удалить зависимость данных человека от `BlogModel`. Профиль должен работать у пользователя, который никогда не создавал блог.
- Данные человека и контекст загружать независимо, где это позволяет интерфейс: ошибка контекста не должна стирать успешно загруженный профиль.

### Блог отсутствует

Вместо карточки блога показать:

> У вас пока нет блога. Создайте блог, чтобы публиковать видео и посты.
>
> Создать блог

- В меню аватара показать «Создать блог» вместо «Управление блогом».
- При прямом переходе в `/studio` без блога показать то же предложение создания, без запросов списка публикаций.
- Использовать существующую форму создания блога, по возможности сохранив её текущий маршрут.
- После создания повторно загрузить контекст и карточку блога, синхронизировать пользовательскую сессию существующим механизмом.
- Учесть частичный успех: в текущем Gateway блог может создаться, а обновление контекста в AuthService — завершиться ошибкой. Повторно проверить наличие блога и восстановить сессию; не предлагать слепое повторное создание.

### Блог существует

- На `/profile` показывать компактную карточку с реальными данными блога и переходом в управление.
- Перенести управление видео, текстами и плейлистами на `/studio`.
- Сохранить действующие возможности: создание, редактирование, удаление, пагинацию и прогресс обработки видео.
- Обновить переходы и возвраты из редакторов. Существующие маршруты форм сохранять либо поддержать перенаправления.
- Кнопки публикации учитывают `permissions`. Для ограничения показывать понятную причину; при отсутствии блога основной сценарий — создание блога.

### Хэдер и будущие разделы

- Аватар открывает меню: личный профиль, управление/создание блога, выход. Настройки показывать только при наличии реализованного экрана.
- Меню закрывается по Escape, клику снаружи и выбору пункта, поддерживает клавиатуру и возвращение фокуса.
- `friendsEnabled` управляет вкладкой «Друзья», блоком друзей и соответствующими действиями.
- `messagesEnabled` управляет вкладкой «Сообщения», иконкой в хэдере и действием «Написать».
- Проверять флаги и при прямом переходе на `/friends` или `/messages`. Выключенный раздел не должен монтировать свой экран и выполнять его запросы.
- Когда появятся реальные API этих функций, проверять флаги также на сервере, используя согласованный источник конфигурации. Скрытия ссылок недостаточно.
- До реализации социальных разделов не переносить в приложение демонстрационные списки друзей и диалогов.

## 6. Общее состояние frontend

- Контекст хранить в общем состоянии приложения, доступном хэдеру, страницам и защите маршрутов.
- Не выполнять отдельный одинаковый запрос из каждого компонента.
- Различать состояния загрузки, успешного ответа и ошибки. До ответа не показывать будущие функции и не отображать ложное предложение создать блог.
- Неизвестные/отсутствующие новые флаги и разрешения трактовать консервативно: функция скрыта, действие недоступно до подтверждения.
- Обновлять контекст после входа, создания блога, восстановления сессии и возвращения фокуса приложению с защитой от избыточных запросов.
- Очищать контекст при выходе и смене аккаунта. Не применять запоздалый ответ предыдущей сессии к новому пользователю.
- При устаревших разрешениях и отказе API обновить контекст и объяснить причину пользователю.
- Обновить OpenAPI и сгенерировать TypeScript-клиенты принятой в проекте командой. Не редактировать generated-файлы вручную.

## 8. Проверки и критерии готовности

- Новый пользователь видит свои данные и предложение создать блог, без вымышленных значений из макета.
- Пользователь с блогом видит его карточку; управление публикациями доступно на отдельной странице.
- «Обо мне» содержит только интересы и дату регистрации. Логотип и круглые аватары соответствуют согласованному варианту.
- Проверены все четыре сочетания флагов друзей и сообщений на уровне контракта и интерфейса. Для ещё не реализованных экранов использовать изолированную проверку механизма, не включение заглушек в рабочем окружении.
- Выключенные функции не появляются при загрузке и недоступны по прямой ссылке.
- Отсутствие блога отличимо от ошибки сервиса; доступны повтор запроса и восстановление после ошибки.
- После создания блога состояние обновляется без повторного входа. Частичный успех не приводит к повторному созданию.
- Контекст не переносится между аккаунтами.
- В текущей версии оба `isAllowed` равны `hasBlog`; проверены состояния с блогом и без него.
- На этапе системы ограничений проверить матрицу запретов видео, текстов и всех публикаций, согласованность контекста и серверных операций, защиту от ручного запроса и устаревшего frontend-контекста.
- Проверены адаптивность, клавиатура, меню, редактирование профиля и сохранность действующих сценариев публикаций.
- Сборка изменённых проектов и целевые тесты проходят. Для контрактов и разрешений нужны содержательные тесты, а не только снимки разметки.

## 9. Правила проекта

- UTF-8 и CRLF для новых и изменённых файлов.
- `AuthFilterAttribute` для авторизации endpoint'ов.
- `ICurrentUserService` для определения текущего пользователя; операции «мой профиль» не доверяют переданному клиентом идентификатору владельца.
- `Result<>` из `Common/Shared/Utils/Result.cs` для ожидаемых бизнес-ошибок; исключения не используются для обычного бизнес-потока.
- Не создавать нежелательную зависимость Domain/Application от `Common/Infrastructure.csproj`.
- Для существующих контрактов сохранить совместимость до перевода потребителей.
